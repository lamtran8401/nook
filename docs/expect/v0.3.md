# Expectation: v0.3

> In short: one release with four parts. The new pack `issue-tracker` brings a Jira ticket or a GitHub issue into the backlog. An area installs its dependencies when they are missing. `nook web` shows a desk in the browser, and the owner decides at the gates there. `nook search` finds words across the wiki, the items and the courses.

The release is done when each scenario passes on a real desk, and `bun run check` passes.
The plan of the release names the slices, the dependencies with their versions, and the order. The owner approves the plan before code.

## Part 1: the pack issue-tracker

`nook init --pack issue-tracker` turns the pack on. Its section of `nook.yml`:

```yaml
issue-tracker:
  backlog: backlog                            # the folder of the tickets; the default
  sources:
    - type: jira
      site: company.atlassian.net
      fields:                                 # the custom fields of this Jira, by their use
        acceptanceCriteria: customfield_10095
        technicalSolution: customfield_10096
        sprint: customfield_10019
      projects:                               # a team with other fields overrides the map for its project
        PAY: { fields: { acceptanceCriteria: customfield_10210 } }
    - type: github
      repo: acme/shop
      prefix: GH                              # issue 482 becomes the item GH-482
      sections:                               # the headings of the issue body, by their use
        acceptanceCriteria: Acceptance criteria
        technicalSolution: Technical solution
```

Each team keeps its acceptance criteria and other details in its own place, so a desk maps them by their use.
`acceptanceCriteria` fills the section Acceptance criteria of `ticket.md`. Each other use gets its own section, such as Technical solution.

| Command | What it does |
|---|---|
| `nook issues pull <ref...>` | reads each ticket and writes `backlog/<KEY>/ticket.md` and `attachments/`; a ref is a Jira key such as `SHOP-12`, or a GitHub issue such as `GH-482` or `acme/shop#482` |
| `nook issues fields <ref>` | lists each field or heading of one ticket with its id or name and the start of its value |
| `nook issues sources` | the sources of this desk, and whether each login works |

The pull reads Jira with `twg jira workitem get <KEY> --full -o json` and `twg jira workitem attachment`. It reads GitHub with `gh issue view <number> --repo <repo> --json` and its comments.
When the pack is on, `/intake` runs `nook issues pull`, then `nook eng item new` for each ticket.

| # | Given | When | Then |
|---|---|---|---|
| T1 | a GitHub source and a `gh` login | the owner types `/intake GH-482` | `ticket.md` holds Fields, Description, Acceptance criteria and Comments; item `GH-482` is in `backlog` with the issue link as its source |

## Part 2: the area install

| # | Given | When | Then |
|---|---|---|---|
| I1 | an area with `install: bun install` and no `node_modules` | `nook eng item verify` runs | the install runs first, then the checks; the run records the install |
| I2 | an installed area whose lockfile changed after the last install | `item verify` or `task prove` runs | the install runs again before the checks or the proof |
| I3 | an installed area with no change of its lockfile | `item verify` runs | no install runs |
| I4 | an install that fails | `item verify` runs | no check runs; the result names the install and its first error lines |
| I5 | an area with no `install` | `item verify` runs | no install runs, as today |

A lockfile is one of `bun.lock`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `uv.lock`, `poetry.lock`, `Gemfile.lock`, `go.sum` and `Cargo.lock`.

## Part 3: the web app

`nook web` in a desk starts the server and opens the browser. Ctrl-C stops it. The first start builds the app.

| # | Given | When | Then |
|---|---|---|---|
| V1 | a desk, in a terminal outside Claude Code | the owner runs `nook web` | the server listens on `127.0.0.1` at the port of this desk, and the browser opens with a one-time token |
| V2 | the browser has the token | it opens the first page | the token becomes an HttpOnly, SameSite=strict cookie; a second use of the token fails |
| V3 | the home page | the owner opens it | it shows the parts of `nook brief`: what waits, what is done, what runs, and each gap of `nook doctor` |
| V4 | items in four states | the owner opens `/work` | one column for each state that holds items; each card shows the id, kind, size, title and criteria |
| V5 | an item in planning | the owner opens `/work/SHOP-12` | the tabs Spec, Plan, Tasks and, when it exists, Walkthrough show the documents with Bench diagrams; the guesses and the open questions show beside them |
| V16 | the walkthrough of a question, with no item, in `work/<date>-<slug>/` | the owner opens its link | the page shows it with the same components |
| V6 | the page of the item | the owner clicks approve | the server runs `nook eng item approve SHOP-12`; the ledger records `owner (viewer)`; a refused move shows its gaps and fixes |
| V7 | the page is open | an agent changes `plan.md` or a slice | the page shows the change within 2 seconds, with no reload |
| V8 | the wiki | the owner opens `/wiki` | the shelves, each index, and each page with its links; the drafts that wait for a yes |
| V9 | a course | the owner opens `/learn` | the cards due, the top patterns of the mistakes, and the scores of each criterion over time |
| V10 | the web app runs | an agent runs `nook web`, or calls its port from Bash | `nook web` refuses to start in Claude Code; the hook blocks the call to the port |
| V11 | the viewer runs | a page reads the desk | it never reads a secret file |
| V12 | the read modules | they run under Node | no read path uses a Bun API; the ledger opens through one SQLite interface for Bun and for Node |
| V13 | the owner types `/view SHOP-12` | the companion answers | it gives the link of the item in the viewer, and builds no HTML file |
| V14 | the owner asks to share the page of `SHOP-12` | the export runs | one HTML file holds the page with its styles inline, and opens from the disk with no server |
| V15 | a second start, with no change of the Nook code | the owner runs `nook web` | the server starts with no build |

When the export covers the pages of a desk, their old builders go in the same release: `nook eng item page` and `nook eng doc page`. `scripts/pages/` stays: it builds the pages of the product docs.
