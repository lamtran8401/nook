Harness Kit · open source · version 0 plan

A base layer for Claude Code that you init into any folder.

Harness Kit gives Claude Code your standards: base rules, templates and packs for work, research, learning, knowledge and reports. You run kit init in any folder. Claude Code stacks the folders, and you add your own context on top.

CLI: kitMIT licencelocal files onlyfor one personneeds Bun and Claude Code
Work

Agents take an item to a result that you accept, in your way, with evidence that you can check.

Learn

You practice a skill every day with your own text, against a real standard, and you see your level go up.

Grow

What you research, learn and decide goes into one wiki that you and the agents both search.

You decide

Only you approve a plan and accept a result. The kit enforces this with hooks and its ledger, not with a polite prompt.

Evidence before trust

Each claim has a source: a test that ran, a file and a line, a rubric score, or your own check.

Markdown for the record, HTML for you

Agents read and write Markdown: specs, findings, wiki pages. When you need to understand something, the visual pack turns it into one page you read once.

Small and replaceable

It uses the native parts of Claude Code. When Claude Code ships a better part, the kit drops its own.

    06

    Layers and init

    The kit has no fixed folder structure. Each folder that you init becomes an environment, and the folders inside it inherit its words and its packs.

    the rule Init a folder to make an environment. Its packs and rules reach every folder inside it.

    Claude Code reads CLAUDE.md and .claude/rules/ from every folder above a session, so words flow down. It reads settings only in the start folder, so hooks and permissions stay where a pack is on.

    ~/Workprojects/who I am, my language, how I write
    company/company rules, what must not leave
    shop/engineering wiki
    its areas and checks; a session here gets all three layers

    Environments nest

    A folder with kit.yml is an environment. A boundary such as company/ is a large one; the folders inside it are smaller ones, and a project is only one of them. You init where you want the packs, and the folders below inherit them.

    ~/Workprojects/          kit init                   who I am, how I write
├── company/           kit init --pack engineering,wiki,jira
│   │                  one ledger and one wiki for the whole company
│   ├── projects/shop/           no init needed: it inherits
│   ├── projects/client-x/  kit init --pack engineering  its own ledger
│   └── wiki/
└── personal/          kit init --pack wiki,learn,research
    ├── english/                  inherits learn
    └── ideas/                    inherits wiki

    The rules of nesting

    • Words flow down. CLAUDE.md and the rules of every environment above a session load, because Claude Code stacks them.
    • Packs flow down. The packs of a folder are the union of every kit.yml above it. A child can add a pack, or turn one off with packs: { off: [jira] }.
    • State stays at the nearest. A pack keeps its record (the ledger, the wiki, the learn files) in the nearest environment that turns it on. Turn a pack on again in a child to give it its own record, like client-x above.
    • Hooks follow the packs, not the folder. Claude Code reads settings only in the start folder, so the kit plugin is on for your user, and each hook finds the nearest kit.yml up the tree before it acts. Where a pack is off, its hooks do nothing.
    • kit doctor shows the environments above the folder, the packs each one gives, and where each record lives.

    One init for a whole boundary

    Init company/ with every pack that you want, and nothing inside. One session there runs /intake, /research and /learn-today on one ledger, one wiki and one set of learn files. The areas in kit.yml are paths below the boundary, such as projects/shop/bff, so one ledger serves many projects.

    Not above two boundaries

    Do not init packs in a folder that holds two boundaries that must stay apart, such as a company and a personal one: one ledger and one wiki would mix their data. Such a folder needs no init at all, or a kit init with no pack for words only. Each boundary holds its own packs and records.

    One environment, many sessions

    One session that does research, learning and engineering all day fills its context. The record is shared, so open one session for each heavy piece of work in the same folder, and join them with /handoff and /pickup. A background session starts in the same folder too.

one repo, one layer

    Many packs, many purposes. A folder turns on as many packs as it needs, and one folder can hold work, notes and learning at once. How you split folders is your choice. Each folder lists its packs in kit.yml, so kit doctor shows what is on where.

    Engineering

    The engineering pack takes one item from the backlog to a result that you accept. This chapter shows its life, the skills of each phase, and the guards.

    What to call one piece of work

    "Ticket" sounds like a bug tracker. The kit needs one neutral word for a commitment with a goal and a definition of done, in any field.

    WordForAgainst
    item (recommended)neutral in every field: a feature, a question, a lesson; short in commands: kit eng item show SHOP-12a little plain
    taskclear to everyonea slice inside an item is also a task, so the word does two jobs
    jobshort, plainsounds like a background process or a cron job
    cardfits a boardthe learn pack uses "card" for spaced review
    briefsays that it starts with a goalreads as a document, not as work that moves

    The id of an item is the key of the tracker (SHOP-12), or one that the kit makes (IT-7). A slice inside an item is T1, T2.

    The life of one item

    Six phases and two gates. Each phase has its state, the stage skill that you type, the craft skills that agents use, and the agents that do the work.

    stage skill: you type it craft skill: agents use it agent your gate a move back

    Read it top to bottom: the phase, the state of the item in that phase, the stage skill, the craft skills, the agents. Three moves go back: reject to cooking, replan to planning, reframe to framing when the goal itself changed. Each move back clears the approval, so the item earns it again. The stages /quick, /auto, /guesses, /handoff and /pickup work in any phase. Block, cancel and restore are not drawn.

    The phases in plain words

    PhaseThe question it answersWhat it leaves behindIt ends when
    IntakeWhat is the work, and is the ticket text safe to read?backlog/SHOP-12/ticket.mdthe item is in the backlog
    FramingWhat do we change, and why? What is "done"?spec.md with acceptance criteriayou confirm the spec
    PlanningHow do we change it, in which order, with which risks?plan.md, tasks.md with slicesyou approve
    CookingDoes each slice work, with a test that can fail?code on a branch, check results, proofsall slices are done and checked
    CheckingIs there a reason to reject? What proves each criterion?marks with graded evidence, the walkthrough pageyou accept
    CloseWhat do we keep for next time?wiki pages, ADRs, follow-up items, commits on requestdone

    28 skills

    12 stage skills that you type, and 16 craft skills that agents use. Each skill is a short hub with side files for the detail, so a deep skill costs no context until it runs.

    10 agents

    Two builders, a verifier, a reviewer, a code reviewer, a scout, a skeptic, and three designers. Builders run as background subagents: at most 4, one for each area.

    Four evidence grades

    run sourced judged owner At the accept, the weakest evidence shows first.

    Branches and worktrees

    An environment is not a git repo; the areas inside it are. So the kit, not Claude Code, gives each item its own place to work.

    CaseWhat the kit doesWhere the builders work
    the first item in an areakit eng item branch SHOP-12 makes the branch kit/SHOP-12-export-filter in each git area of the item and switches the checkout to itin the area folder: projects/shop/bff
    a second item in the same areathe kit adds a worktree of that area: .kit/worktrees/SHOP-14/bff/, on its own branch, with the install step of the area (the lockfile decides)in the worktree; the edit guard sends a builder of that item there and nowhere else
    checks and proofitem verify and task prove run in the checkout or the worktree of the itemthe same place
    commititem commit --run commits on the branch of the item, in its place; never on a protected branch; never a push
    done or cancelledthe worktree goes away, unless it is dirty; then the kit keeps it and says so
    a background session or a subagent of Claude CodeClaude Code makes a worktree only inside a git repo. The kit sets a WorktreeCreate hook, so a session that starts in the environment folder gets the kit worktree of its item instead of nothing

    In v0.1 one item builds in each area at a time, and a second item waits at begin with the gap "area bff is in use by SHOP-12". Worktrees arrive in v0.2, or sooner, the first time two items need the same area.

    Guards that hold the standard

    • Frozen after approve. A change to an approved document stops the next move until a replan.
    • Tests must be able to fail. A new test runs on the base of the branch; a pass there proves nothing.
    • Fresh eyes. The reviewer is not the builder, and it looks for reasons to reject.
    • Quarantine. The scout reads ticket text with no write tools.

    What it never does alone

    • Approve or accept for you.
    • Push, deploy or start apps.
    • Read secrets or .env files.
    • Commit, unless you say yes; then one commit for each slice.

    Research

    The research pack turns a question into findings that you can trust: each answer has its sources, its confidence and its open points.

    What comes out of a question

    OutputWhat it isWhen
    an answer in chata few lines with the sourcesa quick question; no item, no file
    findings.mdfor each sub-question: the answer, the evidence with links or file and line, the confidence, the open pointsevery research item; the record
    references/the raw sources that the analysts opened, saved as they wereevery research item
    a decision recordcontext, decision, consequences, the options not takenwhen the question was a choice
    wiki pagesthe part that lasts: a concept, a lesson, a reference, in our own wordsafter your accept
    an options or report pageoptions side by side, or what we saw, what it means, what to dowhen you ask, or when the options need to sit side by side
    follow-up itemswork that the findings uncoveredwhen there is some

    Research ends in a decision or a fact that others can check. It does not teach you. When the goal is to understand, use /study in the learn pack; it can run a research item for the facts first.

    How an answer is graded

    • High: two sources that do not depend on each other.
    • Medium: one clear source.
    • Low: an inference, marked as such.

    What the analysts get

    One sub-question each, what counts as an answer, where to look, and what is out of bounds. They read in parallel and return only their answer.

    Where it goes

    The findings stay with the question. You accept them; then the lasting part becomes a wiki page, and a decision becomes an ADR.

    Learn

    The learn pack runs a course against a real standard. The first course is English as a working language, aimed at IELTS 6.5 to 7 (about CEFR B2 to C1).

    Two kinds of learning

    A course: get to a level

    • A standard (CEFR, IELTS) and a goal (a band, a date).
    • A placement, a roadmap, the daily and weekly loop above.
    • Scores, a mistake log, cards, a progress page.
    • /learn-setup, /learn-today, /learn-write, /learn-speak, /learn-progress

    A topic: understand something

    • No standard; the goal is that you can explain it and use it. Close to research, but the output is in you, not in a decision.
    • /study the aggregate root in DDD: the facts first (a research item when the topic is large), then explain, one example, a check question, your notes in your own words.
    • Output: a concept page in the wiki, your notes, cards for what you want to keep, a study log.
    • The check is honest: a point counts as learned when you explained it back, not when you read it.

    Rules of the wiki

    • One topic for each page; a long page splits, with links.
    • Each claim has a source: a link, a file and a line, or another page.
    • Nothing secret, nothing about other people.
    • Plain Markdown with [[links]]: it opens in any editor.
    • Agents open the wiki on a condition, not always: when you ask, or when a line of INDEX.md matches the item. The index read is cheap; a page read is not.
    • Version 0 is a convention. A search tool comes when the index is not enough.

    Visual: write and draw for the reader

    Markdown is the record, and what agents read. HTML is what you read: one page that you take in at a glance. The visual pack makes that page for every other pack, from an item, a question, a prompt or a record.

    Two formats, two readers

    • Markdown stays the record: specs, findings, wiki pages, the mistake log. Agents read it; you can read it fast; git keeps its history.
    • HTML is for understanding: a diagram of the real mechanism, a diff with notes next to the lines, a band for each skill over time, options side by side. One local file, no network.
    • A page never replaces the record. It reads the record and shows it.

    What a page can start from

    • an item: /walkthrough SHOP-12
    • a prompt: /walkthrough how does the export job retry?
    • a question and its findings: /research … --page
    • a wiki topic: /page the shipment domain, from the wiki
    • a record: /learn-progress, /report week, /retro

    How a page draws

    FormUsed forPrecision
    inline SVG from the kitdiagrams of a mechanism, before and after, flows, trees, mind mapseach part names its file and line; fixed classes for added, changed and removed; labels you can edit; both themes
    charts as SVG from rowsbands over time, counts for each pattern, minutes against the plandrawn from the record rows, to scale, never from retyped numbers
    Mermaida quick diagram inside Markdown, for a record that agents readfast and plain; the kit sets its theme
    canvasa generated or decorative graphic, rareonly when SVG would be long path data
    the kit componentsthe annotated diff, the criteria table, compare, steps, calloutsbuilt by the tool from git and the ledger; the agent writes only the words

    A drawing answers one question. The detail is in the words and the links next to it, not in a bigger picture.

    Three levels of output, and when a page is worth its time

    A page costs more than a Markdown record, and research, learning and technical work need every detail. So the agent does not make a page by default. It climbs three levels, and it asks before the costly one.

    LevelWhat you getWhenCost
    1 · chatthe answer in a few lines, and what waits for youalways, at the end of every stepnone
    2 · Markdown recordthe full detail: findings with sources, the spec, the lesson notes, the mistake logalways; this is the record, nothing is cut from itsmall
    3 · HTML pageone page to read once: a diagram, a diff with notes, a trend, options side by sidewhen you ask; when a stage calls for it (the walkthrough at accept, the monthly progress); or when the content has a shape that words hideminutes, and tokens

    The rule for large content

    • The agent writes the record first, in full.
    • It shows the summary in chat: the answer, the size of the record, and what a page would add.
    • It asks one question: a page now, later, or not at all. Your answer counts for the rest of the item.
    • A page never drops detail. It layers it: the summary on top, the detail below, the record linked.

    Examples

    • Research: findings.md with every source; in chat, the answer in five lines; a page only when the options need to sit side by side.
    • Learning: the daily review stays in chat and the mistake log; the page comes once a month.
    • Technical: the walkthrough at accept is always a page, because the diff with notes is what you decide on.

    Not a runtime
